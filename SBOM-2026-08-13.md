## Scope and method — read before acting on this

Versions in this document are **observed from the running containers**
(`pip freeze`, `postgres --version`, the ES `/` endpoint, `package.json`),
so they are authoritative for this install.

EOL dates and CVEs were **verified against public advisories on 2026-08-13**
and are cited inline. Everything else is annotated as unverified.

**This is not the output of a vulnerability scanner.** No SCA tool was run.
CVE coverage below is limited to components where a specific advisory was
confirmed; **absence of a CVE entry here is not evidence that a package is
unaffected.** Before making a security claim to anyone else, run a real
scanner — see "Getting authoritative results" at the end.

## 2. Confirmed CVEs

Verified against public advisories on 2026-08-13.

**All confirmed CVEs in this dependency set are now fixed in this repo.**
Each was pinned at a vulnerable version upstream and is overridden in the
`Dockerfile` using upstream's own post-install pattern. Re-verify after any
resync — a future upstream change could reintroduce a pin.

This describes the CVE database on 2026-08-13 rather than a durable
property of the deployment. Two caveats apply:

- The `certifi` and `requests` fixes are installed *in violation of*
  `scaife-viewer-core`'s exact pins; pip reports a dependency conflict and
  proceeds. That is a workaround that happens to hold for leaf packages, not
  a general mechanism.
- Django 2.2 and the packages capped beneath it receive no security patches
  at all, so any newly published CVE in that set has **no in-place fix**.
  The clean state therefore expires on its own, without anyone touching this
  repo. See [`DJANGO-UPGRADE.md`](DJANGO-UPGRADE.md) §6.

| Package | Was | Now | CVEs closed |
|---|---|---|---|
| `gunicorn` | 19.9.0 | **23.0.0** | CVE-2024-1135 |
| `certifi` | 2018.11.29 | **2026.7.22** | CVE-2023-37920, CVE-2022-23491 |
| `urllib3` | 1.26.15 | **1.26.20** | CVE-2023-43804, CVE-2023-45803, CVE-2024-37891 |

### ✅ `gunicorn` 19.9.0 → 23.0.0 — CVE-2024-1135

HTTP request smuggling via improper `Transfer-Encoding` validation: a
front-end proxy and Gunicorn disagree on request boundaries, enabling
restricted-endpoint bypass, cache poisoning and session manipulation.
Affects `>=0.10.0,<22.0.0`; fixed in 22.0.0.

**23.0.0 is the newest release supporting Python 3.9** — gunicorn 26.0.0
requires 3.10+, so this tracks the interpreter ceiling described in
UPGRADE-IMPACT.md. Verified serving: `Starting gunicorn 23.0.0`.

Exposure was low in the default deployment: the application binds to
`127.0.0.1` with no proxy in front, and the attack targets a proxied setup.
Setting `SCAIFE_BIND=0.0.0.0` or adding a proxy would change that.

### ✅ `certifi` 2018.11.29 → 2026.7.22 — CVE-2023-37920 (CVSS 9.8), CVE-2022-23491 (CVSS 6.8)

The pinned CA bundle was **over seven years old** and still trusted roots
since removed for cause: e-Tugra (CVE-2023-37920) and TrustCor
(CVE-2022-23491). Both fixed in 2023.07.22.

`scaife-viewer-core` declares `certifi==2018.11.29`, so pip emits a
dependency-conflict warning and proceeds — the same situation `requests`
was already in. Runtime impact was low (the container firewall rejects
egress and all data is local), but the bundle mattered at image-build time
and for anything reusing this environment for outbound HTTPS.

### ✅ `urllib3` 1.26.15 → 1.26.20

Upstream's `dev` Dockerfile pins `urllib3==1.26.15`, which is affected by
three disclosure issues. We pin **1.26.20**, the final 1.26.x release, which
carries all three fixes:

| CVE | Leak | Fixed in |
|---|---|---|
| CVE-2023-43804 | `Cookie` header on cross-origin redirect | 1.26.17 |
| CVE-2023-45803 | request body retained on a 303 redirect | 1.26.18 |
| CVE-2024-37891 | `Proxy-Authorization` on cross-origin redirect | 1.26.19 |

Staying on 1.26.x is deliberate — urllib3 2.7 requires Python 3.10+, and
this image is 3.9. Revisit if the interpreter moves again.

### 🟡 Everything else

No advisory was confirmed for the remaining pinned versions. Most of the
non-Django Python packages are current (`cryptography` 50.0.0, `lxml` 6.1.1,
`requests` 2.32.5, `PyJWT` 2.13.0, `grpcio` 1.80.0) — the Python 3.9 rebuild
pulled newer wheels for much of the transitive tree. **This is not a clean
bill of health** — it reflects the limits of manual verification.

### Pin conflicts already present

`scaife-viewer-core` declares `requests==2.22.0` and `certifi==2018.11.29`,
but the built image contains `requests` **2.32.5** and `certifi`
**2018.11.29**. So one exact pin is being overridden in the image and one is
not — the dependency set is not internally consistent, and `pip` is not
enforcing it end to end. Worth knowing before treating the declared pins as
the truth; the observed inventory in §4 is what actually ships.

Upstream's `dev` also relaxed several of its own pins during this window
(`elasticsearch` to `>=7,<8`, `PyYAML` to `>=6.0.1`, `requests` to
`>=2.22.0`), so resolved versions now move on their own between rebuilds.
That is why this SBOM records observed versions and is dated.

## 7. Getting authoritative results

This document is a manual inventory. For a defensible vulnerability
position, run real scanners against the built images:

```bash
# Python dependencies
docker exec -u scaife scaife-viewer sh -c 'pip install pip-audit && pip-audit'

# Full image scan (OS + language packages), e.g. Trivy or Grype
trivy image deploy-scaife-viewer:latest
trivy image deploy-morpheus:latest
trivy image sv-postgres:9.6-alpine

# Frontend
npm audit --prefix scaife/scaife-viewer-2026-08-10-001
```

Expect a large report: an EOL Python and an EOL Django alone will generate
findings that cannot be remediated without the upgrade work described in
`UPGRADE-IMPACT.md`.
