# SBOM — Scaife Viewer local snapshot

**Collected:** 2026-08-15 · **Host arch:** arm64 · **Supersedes:**
[`SBOM-2026-08-13.md`](SBOM-2026-08-13.md)

Raw inventory regenerated with `bash scripts/sbom-refresh.sh`. Versions
below are **observed in the running stack**, not read off the pin files.
EOL status and CVE analysis are researched by hand, with sources at the
bottom; the script collects versions only.

This edition follows the platform upgrade completed on 2026-08-14/15. The
previous SBOM described a stack in which five of six platform components
were past end of life. That is no longer the case, and the shape of the
risk has changed completely — from "the platform is unsupported" to "a
handful of dependencies are unmaintained upstream".

## Scope and method — read before acting on this

- **Observed, not declared.** Every version is what `pip freeze`, the
  container and the servers actually report. Where a pin file disagrees
  with reality, reality is recorded and the disagreement noted.
- **This edition was scanned.** All 101 Python packages were queried against
  OSV and every image was scanned with Trivy on 2026-08-15 (§2). Earlier
  editions were not, and said so. A scan is still a point-in-time result
  against those databases, not a guarantee.
- **Reachability is assessed, severity is not adjusted.** Where a finding is
  not exploitable in this deployment that is stated and argued, but the
  CVSS score quoted is always upstream's.
- **Deployment context matters.** This stack is loopback-bound, single-user,
  accepts no untrusted input and blocks egress at the container. Severity
  ratings below are upstream's, not adjusted for that.

## 2. Confirmed CVEs

**All previously recorded CVEs remain fixed.** The overrides that fixed them
survived the upgrade, and two of them are no longer overrides at all:

| Package | Then | Now | Status |
|---|---|---|---|
| `gunicorn` | 19.9.0 → 23.0.0 (post-install override) | 23.0.0 | ✅ CVE-2024-1135 fixed |
| `certifi` | 2018.11.29 → 2026.7.22 (override, **conflicting**) | 2026.7.22 | ✅ CVE-2023-37920, CVE-2022-23491 fixed — and the conflict is gone |
| `urllib3` | 1.26.15 → 1.26.20 (override) | 1.26.20 | ✅ CVE-2023-43804, CVE-2023-45803, CVE-2024-37891 fixed |
| `requests` | pinned `==2.22.0`, overridden to 2.32.5 | 2.34.2 | ✅ metadata now agrees with reality |

The `certifi`/`requests` situation is materially better than it reads above.
Previously `scaife-viewer-core` pinned them to 2018/2019 releases, the image
installed patched versions over the top, and `pip` reported an unresolvable
conflict and continued. Vendoring made those pins editable; they are now
floors (`>=`), and those conflicts are gone.

`pip check` is **not** silent, though. It reports exactly one line:

```
mycapytain 3.0.1 requires typing, which is not installed.
```

That is deliberate. `MyCapytain` declares a dependency on the `typing` PyPI
backport, which is vestigial — the standard library has provided `typing`
since 3.5 — and actively harmful, because the backport *shadows* the stdlib
module and breaks on modern interpreters. The `Dockerfile` uninstalls it
after `pip install`, which is what made the Python 3.12 move possible. The
metadata is wrong; the installed state is right. Removing the declaration
would mean vendoring `MyCapytain` (currently installed from a pinned GitHub
fork), which is not worth doing for a metadata line — but it is the reason
`pip check` cannot be used as a clean/dirty signal here.

### Scan results — 2026-08-15

Unlike previous editions, this one **was** scanned. All 101 installed
Python packages were queried against OSV, and every image in the stack was
scanned with Trivy.

**Application container: no critical vulnerabilities.**

| Scan | Result |
|---|---|
| Alpine 3.24.1 OS packages (Trivy) | 0 at any severity |
| 101 Python packages (OSV) | 1 advisory — see below |
| App image, all scanners (Trivy) | 0 CRITICAL, 2 HIGH — both non-applicable |

The two HIGH findings do not apply. `msgpack` 1.1.2 is pip's **vendored**
copy under `pip/_vendor/`, not an installed package; `setuptools` 70.3.0 is
not present on disk at all (only 81.0.0 is), so it is a layer artefact.

**The one real Python advisory** is on the package we deliberately hold back:

> **CVE-2026-59890** (GHSA-h35f-9h28-mq5c) — `setuptools` < 83.0.0
> **CVSS 3.1 6.1 MEDIUM** — `AV:L/AC:L/PR:N/UI:R/S:U/C:H/I:L/A:N`
> `MANIFEST.in` exclusions can silently fail to match when a filename is
> NFD-normalised and the pattern is NFC, on macOS APFS/HFS+. A file the
> maintainer meant to exclude is then packed into an sdist and, if
> published, uploaded to PyPI.

Not applicable here: this repository builds wheels into a Linux image and
**publishes nothing**. It is also unfixable without other work — see §4c.
`pkg_resources` was removed in setuptools **82.0.0** and the fix landed in
**83.0.0**, so no release both fixes this and provides the module
`pinax-webanalytics` imports.

### Supporting containers: 7 unique critical, all in vendor base images

These are in images we consume rather than build, and none is in the
application container. The count rose from 5 while the *exposure* fell:
the two findings this project could actually act on (nokogiri, and the
kernel headers that `build-essential` dragged in) are gone, and what
replaced them is four perl advisories plus zlib in the upstream Ruby base
image, none with a published fix.

| Image | ID | Package | Fix |
|---|---|---|---|
| `opensearchproject/opensearch:2.19.2` | CVE-2025-14813 | `bcprov-jdk18on` 1.78 | 1.80.2 / 1.81.1 / 1.84 |
| `opensearchproject/opensearch:2.19.2` | CVE-2025-14813 | `bcprov-jdk15to18` 1.78.1 | 1.84 |
| `postgres:17-alpine` | CVE-2025-68121 | Go `stdlib` 1.24.6 | 1.24.13 / 1.25.7 |
| ~~`deploy-morpheus`~~ | ~~GHSA-353f-x4gh-cqq8~~ | ~~`nokogiri` 1.14.3~~ | **fixed** — now 1.19.4 |
| ~~`deploy-morpheus`~~ | ~~CVE-2025-37777~~ | ~~`linux-libc-dev`~~ | **gone** — package no longer installed |
| `deploy-morpheus` | CVE-2026-13221, -42496, -57433, -8376 | `perl-base` (in `ruby:slim`) | none published |
| `deploy-morpheus` | CVE-2023-45853 | `zlib1g` | none (Debian: will-not-fix) |

Reachability, in this deployment:

- **BouncyCastle** is bundled with OpenSearch for TLS and the security
  plugin. Both are disabled here (`DISABLE_SECURITY_PLUGIN=true`, no TLS),
  and the port is loopback-bound.
- **Go stdlib** is inside a helper binary in the Postgres image, not the
  database server.
- **nokogiri** was the most substantive and has been **fixed**: 1.14.3 →
  1.19.4, pinned in `deps/morpheus-combined/Dockerfile`. Verified by the
  byte-for-byte XML goldens in `sv_pdl/tests/test_morpheus.py`, which are
  unchanged across the bump.
- **linux-libc-dev** (kernel *headers*, never a running kernel) is no
  longer installed at all. Gem compilation moved to a `gem-builder` stage,
  so `build-essential` and `libxml2-dev` — and everything they pulled in —
  stay out of the runtime image. That took the morpheus image from 20
  critical findings to 5.
- **perl-base** and **zlib1g** are what remain, both from the
  `ruby:3.4.10-slim-bookworm` base image rather than anything this project
  installs, and neither has a published fix. Nothing in the service invokes
  perl.

## 3. Unmaintained, deprecated, or structurally risky

This is now the main body of risk, and it is concentrated in four Django
add-ons whose *latest release* is already installed. There is no version to
upgrade to.

| Package | Observed | Problem |
|---|---|---|
| `raven` | 6.10.0 | Deprecated by upstream in favour of `sentry-sdk`. Needs `force_text`/`smart_text`, removed in Django 4.0. With egress blocked it can never report anything — the strongest candidate for removal. |
| `pinax-theme-bootstrap` | 8.0.1 (latest) | Needs `force_text` and `Model._meta.installed`, both removed in Django 4.0. Provides the base template every page extends, so it cannot simply be dropped. |
| `pinax-webanalytics` | 4.0.2 | Needs `ugettext_lazy`, removed in Django 4.0. Its `AppConfig` also declares an app label with a hyphen, which Django 3.2+ rejects — replaced locally by `sv_pdl.apps.WebAnalyticsConfig`. |
| `django-webpack-loader` | 0.6.0 | Six majors behind (3.2.4). Untouched deliberately: it reads the webpack 4 stats file the prebuilt bundle ships, and upgrading it is part of the frontend project, not this one. |

Those first three are why `sv_pdl/django_compat.py` exists. It restores four
Django APIs removed in 4.0, is documented as debt rather than a fix, and
`sv_pdl/tests/test_django_compat.py` asserts **which** packages still depend
on it — so the list shrinks visibly as they are replaced, and cannot quietly
become permanent.

### Pins that are now this repository's own

`scaife-viewer-core` and `scaife-viewer-atlas` are vendored into
`packages/`. Their constraints are no longer upstream metadata this repo
must work around — they are editable, and 18 local changes are documented
in `packages/README.md`. Current framework floors:

```

scaife_viewer_atlas:  Django>=5.2,<6   graphene-django>=3.2,<4

                      django-extensions>=3.2.3,<4   django-sortedm2m>=4.0,<5
```

## 4. Python inventory: 101 packages, 75 at latest

26 packages are behind their latest release (28 before the
2026-08-15 `urllib3`/`gunicorn` bumps). They fall into three groups,
and the distinction matters more than the count.

### 4a. Unblocked by this upgrade — no longer constrained (8)

These were held back by Python 3.9 or Django <5.2. Both constraints are
gone, so each is now a straightforward bump that nothing prevents.

| Package | Observed | Latest | Was blocked by |
|---|---|---|---|
| ~~`urllib3`~~ | **2.7.0** | 2.7.0 | ✅ done 2026-08-15 — pin-back removed |
| ~~`gunicorn`~~ | **26.0.0** | 26.0.0 | ✅ done 2026-08-15 |
| `opensearch-py` | 2.8.0 | 3.2.0 | 3.1+ needs Python 3.10+ |
| `django-treebeard` | 4.8.0 | 7.0.0 | 7 needs Django 5.2+ |
| `django-filter` | 23.5 | 26.1 | 26 needs Django 5.2+, Python 3.10+ |
| `django-extensions` | 3.2.3 | 4.1 | 4 needs Django 4.2+ |
| `whitenoise` | 6.7.0 | 6.12.0 | 6.8+ needs Python 3.10+ |
| `django-letsencrypt` | 5.1.0 | 6.0.2 | 6 needs Python 3.10+ |

**`urllib3` and `gunicorn` were done on 2026-08-15.** Both were held by
explicit post-install steps in the `Dockerfile` whose own comments said
"revisit if the interpreter is upgraded". Nothing caps `urllib3` below 2 on
Python 3.12 — `opensearch-py` declares `urllib3<3,>=1.26.19` for
`python_version >= "3.10"`, and `requests` wants `<3,>=1.26` — so the
override was simply removed and pip resolves 2.7.0 directly. `gunicorn` is
now pinned at 26.0.0 in `requirements.txt` and the override is gone.
`certifi` needed no override either, once the vendored core declared a floor
rather than `==`.

That leaves **one** deliberate hold-back in the image, described below.

**`django-treebeard` deserves care rather than speed.** It backs the `Node`
and `Sense` materialised-path trees — the corpus hierarchy the reader and
library traverse — so 4.8 → 7.0 is three majors through the most
structurally central dependency in the stack.

### 4b. Held by an exact pin in the vendored packages (10)

Editable now, but each pin is presumably load-bearing for `core`. Changing
them is a deliberate act, not routine maintenance.

`dask` 2022.1.0 · `google-auth` 1.6.2 · `google-cloud-pubsub` 0.39.1 ·
`grpc-google-iam-v1` 0.11.4 · `google-api-core` 1.16.0 ·
`python-dateutil` 2.7.5 · `python-mimeparse` 1.6.0 · `rdflib` 4.2.2 ·
`ruamel.yaml` 0.17.21 · `wrapt` 1.11.1

`rdflib` 4.2.2 → 7.6.0 is the notable one: it is what MyCapytain stores CTS
metadata in, and its unordered iteration is what made collection labels
non-deterministic until `deterministic_label()` was added
(`DJANGO-UPGRADE.md` §11).

### 4c. Deliberately not upgraded (10)

`Django` 5.2.17 → 6.1 · `django-webpack-loader` 0.6.0 · `dj-database-url`
0.5.0 · `django-redis` 5.2.0 · `django-ratelimit` 4.0.0 · `honcho` 1.0.1 ·
`pinax-webanalytics` 4.0.2 · `psycopg2` 2.9.10 · `rdflib-jsonld` 0.6.0 ·
`setuptools` 81.0.0

**Django stays on 5.2.** It is the current LTS with support to 2028-04;
6.1 is a shorter-support feature release.

**`setuptools` 81.0 is the one remaining deliberate hold-back**, and it is
the only package in the image installed *below* what pip would otherwise
resolve. `pkg_resources` was removed after 81.0. On 2026-08-15 the vendored
`core` and `atlas` were moved to `importlib.metadata`, eliminating two of
the three reasons for it. Exactly one remains:

```
pinax/webanalytics/__init__.py:1: import pkg_resources
```

It cannot be skipped — `site_base.html` loads `pinax_webanalytics_tags`, and
importing that templatetags module imports its parent package. Release 5.0.0
(the latest) has the same line. Removing this pin means replacing or
vendoring `pinax-webanalytics`, which §3 already lists as unmaintained.

## 6. Frontend (npm, build-time)

Unchanged, and deliberately so. The bundle is built once and baked into the
image; nothing in the Python upgrade rebuilt it, and the built assets were
verified **byte-identical** to those produced before any of this work began
(`DJANGO-UPGRADE.md` §11). Node 12, webpack 4 and Vue 2 are all EOL. That is
a separate project of comparable size, and the Django work did not require
it.

## 7. Reproducing the scans

§2's results came from these. Re-run them rather than trusting the table:

```bash
# Python dependencies — OSV, from the host (the container blocks egress)
docker exec scaife-viewer pip freeze | grep -E '^[A-Za-z0-9_.-]+==' > freeze.txt
# then POST each name/version to https://api.osv.dev/v1/querybatch

# Full image scan (OS + language packages), every image in the stack
for img in scaife-viewer-base:latest postgres:17-alpine \
           opensearchproject/opensearch:2.19.2 deploy-morpheus:latest; do
  docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy \
    image --scanners vuln --severity CRITICAL,HIGH "$img"
done

# Frontend (build-time only; nothing here ships at runtime)
docker run --rm -v "$PWD":/w -w /w node:12.13-alpine npm audit --package-lock-only
```

Regenerate the raw version inventory this document is built from:

```bash
bash scripts/sbom-refresh.sh -o inventory.txt
```
